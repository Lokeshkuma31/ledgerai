# 9. Migration Plan

## 9.1 Approach

Every operation below moves from "synchronous / in a client component / not durable" to "dispatched as an event, executed by an Inngest function that orchestrates the same, unchanged engine/service." No business calculation is rewritten — only *where* it runs changes. Migration happens per-operation, not all-at-once, so each can ship and be verified independently; a not-yet-migrated operation keeps working exactly as it does today until its row below is checked off.

## 9.2 What "Implemented" means in this pass

The job platform (`lib/jobs/*`, Prisma models, `/api/inngest`, `/jobs` dashboard, tests) is fully built and wires every function above through real `services/*` calls — no job reimplements business logic. "Implemented" means the Inngest function exists, is registered, calls the correct existing service, and is covered by the idempotency/retry/concurrency design from docs 4/5/7. It does not mean every legacy client-side call site has been repointed to the new event path yet (see §9.3) — both can coexist safely because the legacy paths write through the same idempotent services, so no duplicate data results from both being reachable during the transition.

## 9.3 Explicitly deferred: legacy UI call-site repointing

Per the standing constraint "do not redesign the UI," this pass does not rewrite `ManualSyncButton.tsx`, `EmailDashboard.tsx`, `WorkflowsOverview.tsx`, `SyncDashboard.tsx`, `BankDashboard.tsx`, `AccountAggregatorDashboard.tsx`, `ManualRefreshButton.tsx`, `RecurringOverview.tsx`, or similar components that currently call the legacy `lib/sync/*`, `lib/banks/sync-engine.ts`, `lib/workflows/runner.ts` in-memory paths directly. Repointing a button's `onClick` from a direct engine call to a server action that calls `dispatcher.dispatch()` is a small, mechanical change per component, but doing it for every affected component was judged lower-value than shipping the full, correct platform underneath first — the legacy in-memory paths remain functional (they were already non-durable simulations, unchanged in behavior) while the new async paths are proven out via their own triggers (route handlers, cron, and the `/jobs` dashboard's manual actions). Recommended follow-up: repoint one component at a time, verifying each against the `/jobs` dashboard before moving to the next.

## 9.4 Explicitly deferred: new external integrations

Two categories of "stub" appear above and are called out honestly rather than pretended-complete:

- **Real provider API calls** (Gmail/Graph message fetching inside `sync-run`, bank/aggregator provider APIs, an OCR provider beyond the existing mock, an embedding provider for `semantic-index`) — these require credentials/provider selection decisions outside this platform's scope; the *job orchestration around* them (retry, concurrency, idempotency, dead-letter) is fully built and ready for the real call to be dropped in.
- **Notification delivery channels** (actual email/push sending for `notification-deliver`/`summary-generate`) — no channel provider (e.g. Resend, a push service) exists in the codebase yet; the job records the *decision* to notify (`NotificationCandidate`/`BriefingDeliveryLog`, already durable and idempotent) and stops short of an actual send, consistent with "do not add new financial features" (a delivery integration is new infrastructure, not a migration of existing logic).
