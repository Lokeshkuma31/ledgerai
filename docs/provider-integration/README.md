# LedgerAI — Provider Integration Architecture

**Prepared by:** Principal Integration Architecture review
**Date:** 2026-08-05
**Scope:** Replace every mock provider implementation (Gmail, Outlook, Yahoo, Document OCR, Account Aggregator) with production integrations, entirely behind the existing Plugin Framework, Synchronization Engine, and Inngest job platform. No business logic, UI, or core engine changes.

## Methodology

This design is grounded in direct inspection of the current `master` commit — the four existing provider contracts (`Plugin`, `ConnectionProvider`, `EmailProvider`/`BankConnector`, `OCRProvider`, `SyncProvider`), the already-real OAuth layer (`lib/connections/`), the already-wired Inngest job platform (`lib/jobs/`, per `docs/job-platform/*`), the observability platform (`lib/observability/`, per `docs/observability/*`), and the security posture (`docs/security-hardening/*`). Where the codebase already has a working mechanism — token encryption, retry classification, dead-letter routing, checkpoint-based resume, ownership verification — this design reuses it exactly rather than inventing a parallel one. Where a real gap exists (Plugin Framework's localStorage persistence, Account Aggregator's non-OAuth consent handshake, a Gmail quota-error misclassification bug latent in the generic retry classifier), the gap is named explicitly with its file:line evidence rather than assumed away.

**Ground truth at design time — the single most important finding this set is built on**: the OAuth/token layer (`lib/connections/`) is **already a real, production-grade integration** against Google, Microsoft, and Yahoo's actual endpoints — live PKCE Authorization Code flow, AES-256-GCM encryption at rest, proactive refresh, ownership-checked disconnect/reconnect, full audit trail. What's mocked is **one layer up**: the data-fetch layer (`plugins/gmail/mock-provider.ts` and its Account Aggregator/OCR equivalents) that would use those already-issued tokens to actually call Gmail's API, Microsoft Graph, or an OCR vendor. This materially narrows the OAuth Flow Review (§2) from "design OAuth" to "audit what's real, wire the one new integration point, and build the one genuinely new consent flow (Account Aggregator) that isn't OAuth at all."

## Key findings that shape every document

- **No new unified provider interface is introduced.** The task's requested ten-verb interface (Connect/Disconnect/Validate/Refresh/Sync/Health/Capabilities/Metadata/Status/Version) already exists as the correct union of four contracts split along their real seams — `01` gives the exact mapping and explains why collapsing them would be a regression, not a simplification.
- **A live, latent correctness bug is identified, not hypothesized**: `lib/jobs/retry.ts`'s generic HTTP-403-is-permanent rule will misclassify Gmail's `quotaExceeded` error (also HTTP 403) as a permanent failure indistinguishable from a revoked grant, routing rate-limited syncs straight to the dead-letter queue instead of retrying them. `03` and `04` both cover this; it is the single most concrete pre-implementation fix this review surfaces.
- **Account Aggregator is not an OAuth integration and must not be built as one.** It's a consent-artifact + asynchronous webhook-push protocol (Sahamati/ReBIT spec) with its own ECDH-based data encryption. `02` designs a parallel `createConsentProvider()` factory rather than forcing it through `lib/connections/providers.ts`'s existing OAuth-shaped factory.
- **Yahoo Mail API access is gated behind external partner approval**, not an engineering task — flagged as a rollout blocker in `08` with unknown lead time, separate from Yahoo's identity-only OAuth (already live).
- **The `window.localStorage` persistence gap is wider than one file.** `lib/plugins/registry.ts` was the first instance found, but the identical pattern also backs `lib/email/registry.ts`, `lib/banks/registry.ts`, `plugins/document-intelligence/registry.ts`, `plugins/account-aggregator/consent.ts`, and `lib/sync/scheduler.ts` — all six no-op silently rather than error when read/written server-side, which matters directly for Gmail: `01` §1.2 now names all six as a stage-1 prerequisite, not one.
- **A second live gap an independent review surfaced**: `components/SyncDashboard.tsx`, a Client Component, currently drives `lib/sync/engine.ts`'s legacy in-browser sync path directly (via `lib/email/syncAdapter.ts`/`lib/banks/syncAdapter.ts`), bypassing Inngest entirely. This directly contradicts this set's "Inngest is the only execution path" rule and, left unaddressed, would attempt to call a real provider's fetch layer (and a server-only `decryptToken()`) from the browser the moment a mock is swapped for real. `01` §1.6 now specifies this must be retired or gated before Gmail ships.
- **The quota-limited circuit breaker's health write path needed a design decision, not just documentation** — `deriveHealth()` (`lib/connections/health.ts`) is a pure function with no visibility into `SyncJob` history, so it cannot itself produce a `quota-limited` status the way it produces every other health state. `03` §3.6 and `07` §7.1 now specify this as an explicit override layered on top of `deriveHealth()`'s output, written and cleared by the circuit breaker directly.
- **Most of the rest — Inngest execution for the already-wired sync path, per-org/provider mutex concurrency, dead-letter routing, audit logging, the privacy never-log list, ownership verification — is already correctly designed and built** (`docs/job-platform/*`, `docs/observability/*`, `docs/security-hardening/*`). This set extends those designs to five new providers; it does not re-derive or duplicate them. One exception worth flagging: checkpoint-based resume (§6) is specified against a contract (`SyncJob.lastCheckpoint`) that exists in the schema but is not yet read anywhere by the real Inngest job — `06` now makes clear this is new implementation work, not an existing mechanism being extended.
- **This document set was independently reviewed against the live codebase after first being written**, and the five findings above are corrections made as a result, not hypothetical risks — each was verified by reading the specific cited source file before being written up here.

## What this design explicitly does not do

- Does not modify the `Plugin`, `ConnectionProvider`, `EmailProvider`, `BankConnector`, `SyncProvider`, or `OCRProvider` interface signatures — every real provider satisfies the contract that already exists and is already tested against a mock.
- Does not modify `lib/jobs/{worker,dispatcher,queue,retry,dead-letter,idempotency}.ts`'s public mechanisms — only extends how provider services feed them (correct error classification, quota signals).
- Does not modify `lib/connections/{oauth,token-manager,session,health,engine}.ts` for Gmail/Outlook/Yahoo — that layer is reused unchanged; only Account Aggregator requires new code in this area, additive alongside the existing OAuth factory, not a replacement of it.
- Does not redesign the UI. New Connection Hub states (`quota-limited`) are additive enum values rendered by existing components (`DataSourceStatusStrip.tsx`, `ConnectionsSettingsCard.tsx`) that already render status/health generically.
- Does not write code, pseudo-code, or implementation examples, per the task's explicit instruction.
