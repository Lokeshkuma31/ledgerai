# 6. Risk Assessment

Critical failure modes for a public launch, ranked by (likelihood × impact) given the current, verified state of the codebase. "Likelihood" assumes the app launches **without** addressing the corresponding gap.

## 6.1 Risk register

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | A user disconnects/renames/force-refreshes another user's bank or email connection via the unguarded Server Actions (IDOR) | High | Critical — direct unauthorized access to another user's connected-account state; trust-destroying if discovered by a user or researcher | Fix ownership checks in `lib/connections/actions.ts`/`engine.ts` before launch ([03 §3.2](./03-security-review.md#32-critical-idor-in-connection-hub-server-actions)) |
| R2 | A production incident (error spike, outage, data issue) goes undetected because Sentry/OTel/health checks don't exist | High | Critical — mean-time-to-detection is unbounded; the team learns about outages from user complaints, not monitoring | Wire Sentry + `/api/health` + uptime monitoring before launch ([05](./05-launch-checklist.md#monitoring--observability)) |
| R3 | A long-running sync (email/aggregator) blocks a serverless function past its execution limit, or silently fails with no retry, because it runs inline with no Inngest queue | High | High — failed syncs appear as "nothing happened," eroding trust in a product whose entire value proposition is data freshness | Wire Inngest for all sync/background work before launch ([05](./05-launch-checklist.md#sync--background-jobs)) |
| R4 | Users are onboarded expecting real Gmail/Outlook/Yahoo sync, but the connectors are mocked, and this ships to production undetected | High if untracked | Critical — this is not a bug, it's a product-integrity issue; shipping fixture data as if it were real user email would be a serious trust and potentially legal problem for a fintech product | Real connector implementation is a hard launch blocker, not a fast-follow; explicitly gate "connect Gmail" UI behind the real integration being live, or clearly label it as a preview/demo feature if partial launch is chosen |
| R5 | An account-takeover or credential-stuffing campaign against login succeeds because rate limiting on auth endpoints is unverified/likely absent beyond the generic limiter | Medium | Critical — fintech-adjacent account takeover has outsized consequences (connected bank/email accounts, financial data exposure) | Add dedicated auth rate limiting + verify better-auth's own protections explicitly; consider CAPTCHA or progressive delays for repeated failures |
| R6 | Google suspends or fails to verify the OAuth consent screen because no privacy policy exists at launch, blocking sign-in/connection entirely | High (if unaddressed) | Critical — this isn't a soft risk, it's a hard external dependency; Google's OAuth verification process explicitly requires a live privacy policy URL | Publish privacy policy + terms before requesting Google OAuth production verification; build in lead time (verification review can take days) |
| R7 | A stored-XSS or injected-content vector (AI Coach output, user-uploaded document metadata, merchant names) executes in another user's session because no CSP exists | Medium | High — no defense-in-depth beyond React's default escaping; a single missed `dangerouslySetInnerHTML` or third-party widget becomes exploitable | Add CSP + audit any raw HTML rendering paths ([03 §3.3](./03-security-review.md#33-critical-no-security-response-headers)) |
| R8 | A schema migration against production fails or is destructive because there's no CI gate validating migrations, and no rollback plan | Medium | Critical — data loss or extended downtime on the primary database | Add `prisma migrate diff` CI check + documented rollback procedure ([09](./09-go-live-plan.md)) |
| R9 | Silent data loss because there's no tested backup/restore process (Neon PITR exists but its retention window and an actual restore drill are unconfirmed) | Low-Medium | Critical — unrecoverable user financial data is close to worst-case for this product category | Confirm Neon PITR retention, document restore runbook, perform one real restore drill before launch |
| R10 | A user's request for data export or deletion cannot be honored because no such flow exists, creating a support/legal liability the moment the first user asks | Medium | Medium-High — regulatory exposure scales with user base; better to build before it's urgent | Build export/deletion flows before or immediately after launch, gated by actual jurisdictional/regulatory requirements the business decides on |
| R11 | Yahoo Mail real sync is delayed because Yahoo's mail API requires separate partner approval with unknown lead time (flagged directly in the codebase's own comments) | Medium | Medium — a launch-scope decision, not purely technical | Apply for Yahoo Mail API partner access early, in parallel with other connector work; treat as a hard external dependency with its own timeline, not something engineering can accelerate |
| R12 | Preview deployments leak cross-PR data or break OAuth entirely because Upstash keys aren't prefixed per-branch and OAuth redirect URIs can't match ephemeral preview URLs | Medium | Medium — mostly a developer-experience/data-integrity risk in non-prod, but a preview-environment credential leak (e.g., cached rate-limit state bleeding between PRs) is still worth closing | Key-prefix Redis by deployment/branch; use a stable preview subdomain or disable live OAuth testing in preview ([02 §2.2](./02-deployment-architecture.md#22-environment-separation-requirements)) |
| R13 | A support/security incident happens and there's no audit trail to investigate it (AuditLog model exists, nothing writes to it) | Medium | High — turns every incident into "we don't actually know what happened" | Wire audit logging to sensitive mutation paths before launch ([03 §3.5](./03-security-review.md#35-high-audit-logging-is-schema-only)) |
| R14 | A `tsvector` search column has no GIN index (unconfirmed either way), and search performance degrades badly once real data volume exists | Low-Medium | Medium — a performance/UX risk, not a safety risk, but embarrassing for a "search" feature | Verify the migration SQL directly; add the index if missing ([04 §4.1](./04-performance-audit.md#41-database)) |
| R15 | Accessibility gaps (no WCAG AA validation) create legal exposure (ADA-adjacent claims are common against consumer fintech products) and exclude real users | Low-Medium | Medium | Run an automated + manual accessibility pass before or shortly after launch; `@base-ui/react`'s accessible primitives are a good foundation but not a substitute for verification |

## 6.2 Risk concentration

Most of the critical/high risks above concentrate in exactly the categories flagged as "installed but never wired" in [01](./01-production-architecture.md): observability (R2), background jobs (R3, R13 indirectly), and the connector layer (R4, R11). This is not a coincidence — it means the single highest-leverage phase of pre-launch work is making those five subsystems (Inngest, Sentry, OpenTelemetry-or-equivalent tracing, PostHog, audit logging) actually run, because a large share of the risk register resolves once they do. See [07 — Production Readiness Report](./07-production-readiness-report.md) for how this shapes the phased plan.

## 6.3 Risk not to over-index on

Two things this audit found genuinely solid, worth naming so they aren't re-litigated: the OAuth/token-encryption implementation (`lib/connections/`) is correct AES-256-GCM with proactive refresh and real PKCE — no risk item above touches it because there isn't one; and the Prisma data model / connection-pooling setup is production-appropriate. Effort should concentrate on the gaps, not on re-auditing what's already right.
